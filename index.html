Analytics Engineering · dbt · DuckDB → Snowflake

Modeling private capital, defect by defect.

A dbt project that connects a private-capital deal pipeline to fee revenue across three source systems — a monthly reporting extract, a CRM client master and a billing extract — and ships a handler for every defect it injects.

Engineering surfaces ambiguity with full diagnostic context; resolution is a business decision. A defect the pipeline resolves is a skill demonstration — a defect it can't is surfaced, not silently patched.

↗ View the repo LinkedIn dbt-fusion · DuckDB (dev) · Snowflake (migrating) · MetricFlow

The problem

Why private-capital data breaks the easy assumptions.

A deal isn't an immutable event — it's re-reported every month, so the same deal appears in up to thirteen snapshots and naive counts multiply it. Client identity is fuzzy: one investor shows up under many legal-entity spellings across funds and jurisdictions, and two different entities sometimes share an alias. The reporting schema changed mid-year — a January cutover swapped two strategy columns for four sub-strategy columns and never backfilled the old deals. Money arrives dirty: asset values as currency strings, and roughly a sixth of revenue in non-EUR with no exchange rate. And clients themselves change state over time, so "who was this deal's client at the time" is a point-in-time question, not a lookup. This project injects each of these deliberately — then hands you the handler.

Architecture

Three sources, connected facts — and a parallel QA lane.

The spine runs raw → staging → intermediate → marts. V1 establishes the deal pipeline below; v2 adds a billing branch, shared dimensions and a semantic layer. Identity QA reads before sentinel coercion; invoice QA preserves the evidence before filtering.

The v1 foundation. The dashed teal lane surfaces defects with diagnostic context; the billing branch below extends the same pattern.

V2 · billing and shared dimensions

V2 adds two invoice QA models to the original six. The repository splits invoice staging into stg_fee_prededup and stg_fee_invoice, preserving duplicate evidence before deduplication. dim_service is the conformed service seed; dim_group is derived from the existing client dimension.

V2 · Orchestration

Scheduled monthly, in dependency order.

An Airflow 3 DAG, pc_pipeline_monthly, runs the dbt project on the first of each month in three task groups: staging, then everything downstream of it, then the full test suite. Each group waits for the one before it to succeed, so tests never run against a half-built project.

DAG

Three task groups, one direction

Airflow 3

Written with Airflow 3's @dag, @task_group and @task.bash decorators. Airflow runs in its own conda environment and calls the dbt binary by absolute path, so the orchestrator and the transformer share an interface, not a dependency tree.

why it mattersThe original selectors, stg_+ and mart_+, matched zero models: dbt matches the text before + against exact model names, not prefixes. The tasks would have run nothing and still gone green. Checking each selector with dbt ls before trusting it led to folder selection: staging and staging+ --exclude staging.
RUN

A green run on the scheduler

success

A triggered run completes in about nine seconds. All three tasks succeed on the first try, with no retries needed.

why it mattersThe first scheduled run failed at run_marts. It exposed a bug that manual builds had hidden: the incremental path of mart_fee_revenue was failing on every run, and it only ever looked healthy because manual builds used --full-refresh, which skips that path. The fix went into the dbt model, not the DAG: on_schema_change='append_new_columns'. The enforced model contract still rejects any missing, extra or retyped column.

Defect class 1 · resolved in the pipeline

Five defects the staging layer cleans up deterministically.

These are the mess going in. Each is injected on purpose by the synthetic-data generator, and each has a handler that every downstream consumer would want applied identically — so it belongs in staging.

D1

No stable natural key

resolved in pipeline

The source has no primary key — a deal's only identity is a (location, client, fund) tuple whose fund name drifts across months.

why it's hard hereIdentity has to be reconstructed before anything can join. Hashing a stable business tuple gives every snapshot of a deal the same key; folding the date in would mint a new deal every month.
D2

Periodic-snapshot grain

resolved in pipeline

Every deal is re-reported monthly, so one deal appears in up to 13 rows — naive counts and sums multiply it.

why it's hard hereA dimension row must be point-in-time-correct, not a pile of monthly repeats. Choosing the latest snapshot for the dimension while preserving all snapshots in the fact table is the deliberate call a uniqueness test then guards.
D3

Schema evolution with backfill

resolved in pipeline

A January cutover replaced two legacy strategy columns with four sub-strategy columns — and the source never backfilled the pre-cutover deals.

why it's hard hereThe reconstruction is era-aware: pre-cutover rows are left alone, post-cutover-native deals are trusted, and only genuinely-derivable rows are filled. Where no financing anchor exists, the pipeline flags rather than guesses.
D4

Byte-identical duplicates

resolved in pipeline

~3% of rows per snapshot are exact duplicate rows from a concat-based extract.

why it's hard hereDuplicate snapshot rows would silently double-count every measure. Dedup belongs in staging, keyed on the grain — and because it's fully resolved there, a generic uniqueness test replaces a QA model.
D5

Mixed currency / measure corruption

resolved in pipeline

Asset values arrive as currency strings, and ~16% of revenue is non-EUR with no FX rate supplied.

why it's hard hereNon-EUR revenue can't be converted without a rate, so revenue_eur_equiv is null there — and that null is a signal, surfaced downstream rather than papered over. The raw revenue is preserved for anyone who can supply the FX.

Defect class 2 · surfaced for the business

Six ambiguities the pipeline refuses to guess at.

These can't be resolved by engineering without inventing an answer. Each qa_* model surfaces the affected rows with full diagnostic context and a named resolution owner — the pipeline's job ends at making the ambiguity visible and actionable.

Q1

Unmatched clients

resolved by · Business

A client_name resolves to no alias in the client master, so it can't be stamped to a client.

why it's hard hereOne limited partner appears under many legal-entity spellings across funds and jurisdictions. A name the alias table can't resolve is surfaced for a human, not forced onto a wrong client_key.
Q2

Alias collision

resolved by · Business

One client_name matches aliases belonging to two different clients — the join fans the deal out.

why it's hard hereTwo distinct legal entities registered the same alias string. Engineering can detect the fan-out but can't decide which entity is right — so the model reports it with both candidate client_ids attached.
Q3

Unresolvable strategy

resolved by · Business

A pre-cutover deal marked real_estate or infrastructure has no private_equity / private_debt anchor to backfill from.

why it's hard hereThe backfill in Defect 3 needs a financing-type anchor. When none exists the sub-strategy is genuinely underivable — the pipeline flags it 'strategy_unresolvable' and surfaces it here for manual classification.
Q4

Strategy / service changes

resolved by · Business

A strategy or service column changes value across a deal's monthly snapshots.

why it's hard hereProves dim_deal's latest-snapshot treatment is a deliberate choice, not silent data loss. '!=' skips null-touching transitions on purpose — the cutover NULL -> value boundary is not a real change.
Q5

Ambiguous strategy change

resolved by · Business

A pre-cutover deal's sub-strategy changes after the backfill snapshot — indistinguishable from a late backfill correction.

why it's hard hereStaging cannot tell a real strategy update from a late backfill fix on these columns. Rather than pick one and be silently wrong, the pipeline surfaces the ambiguity. (Zero rows by generator design — the invariant is that none leak in.)
Q6

Terminal measure gaps

resolved by · Business

A deal in a terminal state (Won / Lost / Rejected) has a null revenue or null asset.

why it's hard hereA closed deal should have been measured. The null is checked on RAW revenue/asset (not the EUR-equivalent) so a currency-conversion gap is never mistaken for a data-entry gap — resolution means correcting the source.

V2 · from pipeline to revenue

A Won deal is the beginning of the billing story.

The September v2 spec extends the v1 foundation with invoice-line data. Only clients with Won deals generate invoices; the generator derives that population from pns_raw_manifest.json and uses service selections at the first Won snapshot.

V2

The date a deal becomes terminal

pns_raw addition

status_change_date records when a deal becomes Won, Lost or Rejected. It is null for non-terminal deals and cannot fall after the first snapshot carrying the terminal status.

why it mattersThe interval from a Won status change to the first invoice measures pipeline-to-revenue lag. Billing periods start in the month after the client's earliest Won date and run through August 2026.
A / E

Stage invoices before deduplicating them

staging

The grain is invoice_id: one client, one service and one billing period per invoice line. Multiple lines can share the same client, service and invoice date. Staging casts dates, timestamps, amounts and payment flags, then derives two fields.

About 3% of raw rows are exact duplicates; about 8% are negative credit notes. stg_fee_prededup retains the evidence for QA, then stg_fee_invoice selects one row per invoice.

why it mattersfee_line_type separates gross invoices from net revenue after credits. billing_period_label comes from the period being billed, not the invoice issue date. fee_basis is a category (AUM, commitment, flat or NAV); it is never summed.
C

Late arrivals follow the extract timestamp

incremental model

About 5% of invoice rows arrive more than 45 days after their invoice date. The incremental filter uses source_extract_timestamp; merging on invoice_id keeps the invoice identity stable across runs.

why it mattersAn invoice-date cutoff would miss old invoices newly present in the extract. The current mart stores invoice rows; the v2 spec defines the monthly revenue view by client, service and billing period. The MetricFlow definitions below describe that analytical contract.
Q7

Duplicate invoice evidence

dedup + QA

qa_duplicate_invoices lists repeated invoice IDs and their occurrence counts before staging removes the duplicates.

why it mattersThe revenue model receives unique invoices while the QA lane keeps the extract re-run visible. Querying the deduplicated model would erase the evidence this check needs.
Q8 / D

Unrecognized service codes

surfaced for review

About 3% of rows carry an unknown code such as SVC-OTC. qa_unmatched_services surfaces those rows; int_fee_invoice joins recognized codes to dim_service and attaches service_name and pns_column_name.

why it mattersUnknown services are excluded from mart aggregations. There is no service sentinel: the pipeline cannot safely attribute an unknown code to a billable category. The affected invoices remain visible in QA for reconciliation.

MART

Revenue, retention and cohorts

three analytical views

All three marts read the recognized-service invoice stream from int_fee_invoice. The v2 spec defines a distinct question for each:

  • mart_fee_revenue — gross invoices and net fees after credit notes, analyzed by client, service and billing period; refreshed incrementally.
  • mart_client_retention — clients active in period N, retained in N+1, or absent in N+1, at client-and-period grain.
  • mart_cohort_revenue — revenue by onboarding quarter and periods since the first invoice, compared with the cohort's period-zero baseline.
why it mattersPeriod revenue, client continuity and cohort performance answer different questions. Keeping separate models makes their grains and denominators explicit.

V2 · MetricFlow contract

Four semantic models, seven metric definitions.

The v2 spec puts shared measures and metric definitions above the marts. Three semantic models describe billing; a minimal addition to the existing deal fact supplies AUM for fee_yield.

SEM

One definition for each analytical measure

  • sem_fee_revenue → mart_fee_revenue: gross and net fee amounts, invoice count and credit-note count. Service, billing period, fee basis and payment status provide the analysis dimensions.
  • sem_client_retention → mart_client_retention: distinct active, retained and churned clients by billing period.
  • sem_cohort_revenue → mart_cohort_revenue: cohort gross revenue and active cohort clients by onboarding quarter and period offset.
  • sem_deal_snapshot → fact_deal_snapshot: aum_eur, restricted to a single reporting date for cross-model comparison.
METRIC

Revenue quality and client continuity

v2 definitions

These definitions follow the September v2 spec. Gross and net revenue stay distinct, and retention ratios use explicit billing periods and cohort baselines.

Tests that prove it

The invariants that keep the model honest.

A selection from the suite — the assertions that guard grain, cross-source consistency, slowly-changing-dimension integrity, and the completeness of the QA surfacing itself.

TEST

SCD Type 2 integrity

Three assertions guard the client history: exactly one current row per client (below), the current row has a null effective_to, and version windows are contiguous with no gaps or overlaps.

TEST

Cross-source client_type consistency

The client_type reported on the pns side must match the authoritative dim_client value. Configured severity: warn — a mismatch is a data-quality signal to investigate, not a hard pipeline failure.

TEST

Grain / no fan-out on the deal-client join

Every deal must resolve to exactly one current client. COUNT != 1 catches both fan-out (a deal matching multiple clients) and orphans (a deal matching none) in one assertion.

TEST

Exhaustive surfacing invariant

Every deal the backfill flagged 'strategy_unresolvable' must appear in qa_unresolvable_strategy. If the flag ever shows up somewhere the QA model doesn't account for, the backfill logic has a bug — the test fails.

Modeling decisions

Four calls, and the alternative each one rejects.

01

Surface ambiguity, don't impute it.

rejected Guessing a value to keep the marts looking clean.

Where identity or strategy is genuinely undecidable, the pipeline flags it (CLIENT-000, strategy_unresolvable) and routes it to a QA model with a named business owner. Imputing a value would manufacture false precision and hide the problem from the only people who can actually resolve it.

02

A CLIENT-000 sentinel over NULL propagation.

rejected Leaving client_id NULL on unresolved deals.

int_pns_deals coerces both unmatched and collision deals to a single CLIENT-000 client (client_key = -1) so every fact row still joins and every deal is counted. A NULL would silently drop deals from inner joins and break point-in-time client_key resolution.

03

QA models read staging / intermediate, never the marts.

rejected Building the QA models off dim_deal.

Each qa_* model taps stg_pns or int_backfill_anchor directly, keeping full diagnostic context and staying insulated from the CLIENT-000 coercion the marts apply. Reading from dim_deal would couple diagnostics to the business layer and discard the very detail a human needs to resolve the issue.

04

A deterministic key that's stable across time.

rejected Hashing reporting_date into the deal key.

deal_id is hashed from (location, client_name, fund_name) with the snapshot date deliberately excluded, so a deal keeps one identity across all 13 months. Including the date would mint a brand-new deal every snapshot and destroy the periodic-snapshot grain the whole model depends on.

Stack & roadmap

Built to move from a laptop to a warehouse.

dbt-fusion DuckDB · dev Snowflake · migrating MetricFlow Airflow 3

Developed on DuckDB for fast local iteration; the model is warehouse-portable and is being migrated to Snowflake as the production target.

  • Snowflake migration — porting the model off DuckDB to a production warehouse (in progress).
  • September v2 scope — status-change dates, invoice staging and QA, timestamp-based incremental loading, conformed services and group-level analysis.
  • MetricFlow semantic layer — four semantic models and seven defined metrics for revenue, credit notes, retention, cohorts and fee yield. AUM is semi-additive and must be restricted to one reporting date.
  • Airflow orchestration — a monthly DAG runs staging, downstream models and tests as three dependent task groups.
